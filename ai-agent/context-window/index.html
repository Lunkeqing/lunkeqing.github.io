Context Window: The Model's Whiteboard (and Why 1M Isn't a Free Pass)

Every model launch now brags about context length. “1M context window!” sounds like the model can swallow an entire book series in one gulp.

But 1M is not a free pass. Here’s the reality check: if you stuff 900K tokens of input into a 1M window, you only have ~100K left for the output. And even if you somehow fill all of it, the model won’t “remember” everything equally well.

So what is a context window, really? And why does it behave in all these counterintuitive ways?

The Whiteboard
#

Imagine your brain has a whiteboard for meetings. Its size is fixed: say, 100 lines.

You write meeting notes on it as the discussion goes. The more you write, the less space is left for new notes. When it’s full, you either erase old content (lose information) or you can’t write anymore (error).

The model’s whiteboard is its context window — the total token budget for a single request. And “a single request” means everything:

context window = your input (system prompt + chat history + current question) + the model's output

Input and output share the same whiteboard. This is the #1 trap for beginners: a 128K window is not 128K of input plus 128K of output. It’s 128K total, split between them.

Why Do They Share the Window?
#

Good question. And the answer isn’t “because the API was designed that way.” It follows directly from how LLMs actually work.

Remember from the previous post: an LLM is an autoregressive “word chain”: it predicts one token at a time, appends the result to the input, and predicts the next one, over and over until it stops.

That means: every output token immediately becomes part of the input for the next prediction. The output is written back onto the whiteboard and read again.

So the output must occupy window space. It’s not a design choice — it’s the geometry of autoregression. The output of this round is the input of the next round.

Working Memory, Not a Hard Drive
#

A context window is working memory, not storage.

  • Your hard drive can hold a million files. Nothing gets “erased” until you delete it.
  • A whiteboard holds only what fits right now; old notes are gone once erased.

The model is amnesiac between requests: it only sees what you put in this time. Every request is a fresh start. The window is the only thing it can see, and it’s finite.

That single fact explains almost every “weird” behavior below.

Three Hard Questions
#

Q1: What Happens When It’s Full?
#

Two things, both bad:

  1. Truncation: the request errors out, or the input gets silently cut. The model never sees what you didn’t fit.
  2. Output truncation: if the model hits its max_tokens limit mid-answer, it stops. The response is cut off without an error: the API just reports finish_reason: "length" instead of "stop".

That last one is a classic production gotcha: your app thinks the answer is complete, but it’s actually a half-finished thought. Get into the habit of checking finish_reason.

Q2: 1M Is Big — So Bigger Is Always Better, Right?
#

Nope. There’s a well-documented problem called lost in the middle (Anthropic calls it context rot): the model remembers the beginning and end of the window much better than the middle.

Think about a long meeting. You remember how it started (agenda) and how it ended (action items). But ask yourself what was discussed at minute 47, and you’re lost. Same with the model: the middle of the window is where information goes to be forgotten.

The bigger the window, the more content sits in that “forgotten middle zone.” Official docs now openly admit: carefully curating what goes into the context matters more than how much space you have. More context is not automatically better.

Q3: Why Does a Bigger Window Cost So Much More?
#

This is where it gets counterintuitive. You’d think “bigger window = just more storage = linear cost.” But attention is O(N²):

For every token, the model must compute a relevance score against every other token in the window. That’s N × N = N² computations.

Going from 128K to 1M is an 8× window increase, but a 64× increase in computation (8²). That’s why long contexts are slow and expensive: it’s not storage, it’s a quadratic explosion in compute.

Industry workarounds exist (sparse attention, linear attention, sliding windows; Kimi’s “hybrid linear attention” is one), but they’re engineering trade-offs, not free lunches.

Managing Long Context
#

Three classic strategies, and when to use each:

StrategyWhat it doesWhen
SummarizeCompress old history into a few sentencesWhen the gist matters, details don’t
TruncateDrop the oldest contentCrude but effective for FIFO chat
Retrieve (RAG)Only pull in relevant chunksWhen you have a big corpus: search, don’t stuff

The retrieval one is the big idea: with 1M windows, people often ask “do we still need RAG?” Yes — not because we can’t fit the data, but because the model can’t use 1M tokens well. Retrieval isn’t about capacity; it’s about focus.

TL;DR
#

A context window is the model’s whiteboard: input and output share it, it’s finite, it’s working memory not storage, bigger isn’t always better (lost in the middle), and bigger is definitely more expensive (O(N²) attention). Manage it like a whiteboard: summarize, truncate, or retrieve — don’t just stuff it.
